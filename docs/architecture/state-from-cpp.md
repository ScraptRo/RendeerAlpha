# Reading and writing state from C++

State is declared in TypeScript, like everything else an application declares:

```ts
export const state = {
  count:   { value: 0, doc: "how many times a button has been pressed" },
  details: false,
  notes:   "",
}
export const commands = { save: "write the notes out" }
export const tables   = { products: { title: "", price: 0, inStock: false } }
```

A field's type is whatever its initial value is, which removes the ceremony of saying it
twice; `{ value, doc }` takes the place of a bare value where one wants documenting.

One thing this costs: generating the header now needs esbuild, where an XML
declaration needed nothing. A machine building without node can still use the XML
form, which the reader accepts and nothing else does.

That generates a header into the build tree. Include it, and every signal is a pair of
typed functions:

```cpp
#include <RdaState.h>          // generated by rda_add_state

RDA::State::define();          // once, in onStart, before the layout opens

const double n = RDA::State::count();
RDA::State::setCount(n + 1);
RDA::State::setDetails(true);
RDA::State::setText_box("hello");
```

The names come straight from the declaration: `<number name="count"/>` becomes `count()`
and `setCount()`. The accessors hold the signal id rather than looking the name up, so a
read is an array index and not a hash of a string.

A write from C++ is the same event as a write from a handler in a layout. It marks the
bindings that read that signal, and the next frame evaluates them and asks for a redraw.
Nothing has to be told that the interface changed, and no widget is searched for.

**Which thread.** The signal table has no locking, so write from the loop thread — inside
`onStart`, `onUpdate`, or an event handler. From a worker thread, hand the write to the
loop instead, which runs it there and returns once it is done:

```cpp
loopWork().request([] { RDA::State::setCount(42); });
```

**Going the other way.** A widget hands its handler the new value, and a handler — unlike
a value binding — may name one parameter to read it:

```tsx
<textfield
  text={() => state.notes}
  onChange={(typed) => state.notes = typed}
/>
```

That parameter is the only name in a handler that is not `state.<something>` or a literal.
It compiles to a single `push.event` instruction, so the handler still carries no closure
and no interpreter. A value binding is called with nothing, so naming a parameter there is
refused where it is written rather than failing later.

The type of the parameter comes from the widget schema — `string` for a text field,
`boolean` for a checkbox, `number` for a slider — so assigning it to the wrong signal is
a TypeScript error before anything is compiled. Naming it is optional: a handler that does
not want the value simply takes none, which is what every existing `onClick` does.
