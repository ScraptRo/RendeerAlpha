# RendeerAlpha

Glue between an application's backend and its interface.

The interface is written in TypeScript and compiled ahead of time into a flat binary
blueprint. The application that loads it contains no parser and no JavaScript engine — it
reads a buffer and builds widgets. The backend is ordinary C++ that owns the GPU device
directly, in its own process, without a bridge in the way.

```tsx
export default function Hello() {
  return (
    <stack id="root" arrange="vertical" spacing={8} padding={12}>
      <label id="title" height="content"
             text={() => `Clicked ${state.count} times`} />
      <button id="add" text="Add one" height="content"
              onClick={() => state.count++} />
    </stack>
  )
}
```

Those `{() => ...}` thunks are not closures that ship. They are parsed at build time into
stack bytecode over `state`, so the running program is reactive without carrying a
JavaScript engine: writing `state.count` marks exactly the bindings that read it, and the
next frame evaluates only those.

## What is in here

The engine and its toolchain, and nothing else. An application is a separate project
that points at this checkout, so cloning this gets a library rather than a library plus
somebody's demos. [Your first interface](docs/setup/first-interface/README.md) is the
shortest way to see one.

## Build

```bash
scripts\windows-bringup.bat        # or ./scripts/linux-bringup.sh
```

Once. The bring-up checks what is installed and names what is missing, builds the
engine, runs its tests, and leaves the result in `bin/`: the engine as a shared library,
the `rda` tool that compiles an interface, and the engine's own assets. It also registers
the Python and Node packages with whatever interpreters it found, so a project in either
language builds nothing but its own interface.

`scripts/build.bat` and `scripts/test.bat` (`.sh` on Linux) are the same steps one at a
time. The tests are two kinds of thing: the engine's own cases, which need no device, and
the three binding tests, which start a real engine and briefly open a window. Each of
those three skips itself with a reason when Python, node, koffi or dotnet is not
installed.

## Use it from an application

One line, and no install step:

```cmake
add_subdirectory("path/to/RendeerAlpha" rendeer)

add_executable(myapp main.cpp)
target_link_libraries(myapp PRIVATE rendeer)

rda_add_state(myapp res/state.ts)
rda_add_theme(myapp res/themes/mytheme.ts)
rda_add_types(myapp res/layouts/rda.d.ts res/themes/mytheme.ts res/state.ts)
rda_add_layouts(myapp res/layouts/main.tsx)
```

That gives a C++ application the library, the `rda` tool, and the build rules that
compile its interface. A project in another language has no CMake at all: it points at
`bin/`, and `rda build .` does for its `res/` what those four rules do.
[Adding it to a project](docs/setup/adding-to-a-project/README.md) shows each shape.

Run one, click a button, edit a label in its layout, and save. The interface rebuilds
while it runs; the count survives, because state lives in the application rather than
inside the thing being replaced.

## The backend does not have to be C++

The interface layer is reached through a C ABI as well, so a backend can be written in
anything with an FFI. Python, Node and C# all have a package here already:

```python
import rda
from state import State, Commands, define    # generated by `rda python`

@Commands.save
def on_save():
    print(State.notes)

config = rda.StartupConfig()

@config.on_start
def opened():
    define()
    rda.load_interface("res/layouts/home.rdab")

rda.init(config)
rda.wait()
```

Or the same thing in Node, where `init()` returning means a server and a window are one
program:

```js
import * as rda from 'rda'
import { State, Commands, define } from './state.mjs'   // generated by `rda node`

rda.init({ theme: 'res/themes/app.rdth' })
define()
rda.loadInterface('res/layouts/home.rdab')

Commands.save(() => console.log(State.notes))

await rda.run()
```

Or C#, where the generated state makes a misspelled signal a build error:

```csharp
using Rendeer;
using RdaState;              // generated by `rda csharp`

Rda.Init(new StartupConfig { Theme = "res/themes/app.rdth" });
Schema.Define();
Rda.LoadInterface("res/layouts/home.rdab");

Commands.save(() => Console.WriteLine(State.notes));

Rda.Wait();
```

Same layouts, same theme, same router, same animation. A backend declares state, writes
it, answers commands and fills tables; it does not draw, which is why the seam is at the
state rather than at the pixels.

## Requirements, in short

A C++20 compiler, CMake 3.21+, and the Vulkan SDK — which on Windows is the only install,
because it carries Vulkan, shaderc and glm together. GLFW is built from source if it is not
already there. On Linux the four are packages. The bring-up script for each platform
checks for all of it and prints the `winget` line or the `apt` package for whatever is
missing.

Compiling an interface needs esbuild, a single static binary the bring-up puts in `bin/`
— downloaded from the npm registry if there is no node to get it from. It is a
**build-time** dependency and only that: it transforms a `.tsx` before the layout
compiler evaluates it, and nothing that ships contains a parser or a JavaScript engine.

A Python backend needs Python 3.8+ and nothing compiled — the binding is ctypes. A Node
backend needs Node 18+ and one `npm install`, which links the package from the checkout
and brings koffi, the FFI, with it. A C# backend needs .NET 8+ and nothing else: the
binding is two source files you compile in. In every case the engine is a shared library
the backend opens, not the other way round.
