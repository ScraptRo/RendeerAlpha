# rda — a RendeerAlpha backend in Python

```python
import rda
from state import State, Commands, define   # generated by `rda python`

config = rda.StartupConfig()
config.name = "My application"
config.theme = "res/themes/app.rdth"

@Commands.add_one          # a handler may be written here, before anything starts
def add_one():
    State.count += 1

@config.on_start
def opened():
    define()                                  # the names the layout was compiled against
    rda.load_interface("res/layouts/home.rdab")

rda.init(config)           # the engine runs on its own thread; this returns
rda.wait()                 # ...until there is nothing left to do but let it live
```

Python is a **backend**. The interface is a compiled layout — written in TSX, checked
against a generated schema, styled by a theme, bound to signals and animated by the
engine. Python does not draw it: it loads it, writes the state it reads, and answers the
work it asks for. That is the same job C++ has, and the layout cannot tell which of them
is behind it.

## What you need

* `rendeer_c.dll` (`librendeer_c.so`), which the engine's bring-up script builds and
  stages into the checkout's `bin/`. The package finds it there; `RDA_ENGINE` names
  another one.
* `state.py`, generated from the same declaration everything else is:
  `python -m rda build .` in your project.
* This package on the interpreter's path. The bring-up registers it with the
  interpreter on `PATH` by writing one `.pth` file; in a virtual environment,
  `python <checkout>/bindings/python/register.py` or `pip install -e <checkout>/bindings/python`.

There is no extension module to build, and nothing compiles. `python -m rda where`
prints which engine an interpreter would use.

## Generated, not dynamic

Every signal is a real property on `State`, with the type and the documentation the
declaration gave it. `State.ARandomValu = 1` is an `AttributeError` where it is written,
not a value that quietly goes nowhere — the same guarantee the generated C++ and the
generated TypeScript give their languages.

## Tables

The rows a `<list>` shows. A signal holds one value; this holds ten thousand, and showing
them costs about as many widgets as fit on screen rather than ten thousand.

```python
Tables.products.fill([
    {"title": "Widget", "price": 9.0, "inStock": True},
    {"title": "Gadget", "price": 12.5, "inStock": False},
])

Tables.products.rows              # 2
Tables.products.title(0)          # "Widget"
Tables.products.set_price([19.0], first=1)
Tables.products.rows = 100        # grow; new rows are zero, false and empty
```

A row may be a **mapping**, an **object with those attributes**, or a **sequence in column
order** — whichever the application already has, whether that is a database row, a
dataclass or a CSV line.

`fill()` writes a column at a time, and that is not an optimisation detail. Every call
crosses to the engine's loop thread and waits, so ten thousand rows of three columns is
three round trips this way and thirty thousand the other. Measured: about 35 ms.

## Screens

```python
rda.set_transition_ms(180)
rda.open_routes(ROUTES, "res/layouts")

State.route = "catalogue"     # navigating is an ordinary write
rda.back()                    # or drive history from outside the interface
rda.can_go_forward()
```

`ROUTES` is generated from the declaration, in declaration order, so the first entry is
where the application opens unless `route` already says otherwise.

## Asking for a command yourself

The interface is not the only thing that can want work done. `rda.invoke("save")` runs the
same handler a button would, for a menu, a hotkey or a scheduled job -- and it is refused,
rather than ignored, when nothing is bound to that name.

## Threading

`init()` starts the engine on a thread of its own and returns **once it is up** — the
window and the renderer ready, and your `on_start` finished. So the line after it may
write state and expect it to exist, and the interpreter stays yours: a REPL, a web server
or a data pipeline carries on while a window is open.

Every call here is safe from any thread. The engine's state belongs to its loop thread, so
each call hands its work across and waits — which costs a frame, and is the right price
for a backend that reacts to events. Handlers run *on* the loop thread, so calls made
from inside one are free.

That last point is where Python has it easier than Node: ctypes will happily call a Python
function from a foreign thread, so a command can be a real callback. The Node binding
cannot do that and collects commands from a queue instead — see
[the Node page](../../docs/backend/node.md).
