# rda — a RendeerAlpha backend in C#

```csharp
using Rendeer;
using RdaState;              // generated by `rda csharp`

Rda.Init(new StartupConfig { Name = "My application", Theme = "res/themes/app.rdth" });
Schema.Define();
Rda.LoadInterface("res/layouts/home.rdab");

Commands.save(() => Console.WriteLine(State.notes));

Rda.Wait();
```

C# is a **backend** here. The interface is a compiled layout — written in TSX, checked
against a generated schema, styled by a theme, bound to signals and animated by the
engine. C# does not draw it; it loads it, writes the state it reads, and answers the work
it asks for. That is the same job C++ has, and the layout cannot tell which of them is
behind it.

## Installing

Nothing. The binding is two source files and the engine is a shared library:

```xml
<ItemGroup>
  <Compile Include="path/to/RendeerAlpha/bindings/csharp/Engine.cs" />
  <Compile Include="path/to/RendeerAlpha/bindings/csharp/Rda.cs" />
  <Compile Include="$(RdaGenerated)/state.cs" />
</ItemGroup>
```

Two files rather than a NuGet package, because that is a lot of machinery to avoid
copying two files — and compiling them in means what you build is what is in the
checkout, not an artefact from some earlier one. `Rda.csproj` is here if you would rather
reference a library.

`state.cs` comes from `rda build <project> --csharp`, which your `.csproj` runs before
compiling; the same `.csproj` copies `rendeer_c.dll` and the engine's `res/` from the
checkout's `bin/` beside the executable. [A C# project](../../docs/setup/adding-to-a-project/csharp.md)
is that file. There is no CMake anywhere in it: a .NET application is built with
`dotnet build`.

Targets `net8.0`, and uses nothing newer.

## What C# gets that the other bindings do not

**A row is a struct, so the compiler checks it.** Python and Node take a mapping and find
out at run time whether the keys were right. Here:

```csharp
Tables.products.Fill(new[] {
    new Tables.products.Row { title = "Widget", price = 9.0, inStock = true },
});
```

A misspelled column does not compile. The same is true of a misspelled signal —
`State.notAThing` is not a member, so the mistake the other two bindings catch when the
line runs is caught here before it exists.

## The names look wrong, and that is on purpose

`State.count`, not `State.Count`. The declaration's names are used exactly as written,
which is unusual for C# and deliberate: `state.count` in a layout, `State::count()` in
C++, `State.count` in Python and `State.count` here are **one signal**. A generator that
renamed things would make every reader translate between two spellings of the same name.

A declared name that collides with a C# keyword is emitted as a verbatim identifier —
`@class`, `@int` — rather than renamed, for the same reason.

## Two things P/Invoke gets wrong by default

Both are handled inside `Engine.cs`; they are written down because anyone extending the
binding will meet them.

**Strings are UTF-8 on this ABI, and a bare `string` parameter is not.** The default
marshalling is ANSI. Written that way and read back, `"éàü — café"` returns as U+FFFD
replacement characters: the text is destroyed on the way in, silently, and only for the
inputs an English test never uses. Every string going out carries
`[MarshalAs(UnmanagedType.LPUTF8Str)]`; every string coming back is read as `byte[]` and
decoded here. Measured both ways before the binding was written.

**A delegate handed to native code must outlive the call that registered it.** The
collector cannot see that the engine is holding the function pointer, so a trampoline that
goes out of scope is collected and the next click calls into freed memory. Every one is
kept for the life of the process.

`CallingConvention.Cdecl` is declared explicitly too. On x64 there is only one convention
and it makes no difference; on x86 the default is StdCall and this ABI is not, which is a
stack corruption rather than an error message.

## Commands are real callbacks

Unlike Node. The CLR takes a call from a foreign thread happily — **measured**, with the
engine reaching a C# delegate on its own loop thread — so a command handler is an ordinary
delegate that the engine invokes inside the frame the interface asked in.

Which means a handler should be quick, and must not block on anything the loop is
responsible for. Hand slow work to a `Task` and let the frame go.

```csharp
Commands.save(() => { ... });          // typed, from the generated file
Rda.OnCommand("save", () => { ... });  // by name, when the name is only known at run time
Rda.Invoke("save");                    // ask for it yourself: a menu, a hotkey, a job
```

## Threading

`Init()` starts the engine on a thread of its own and returns **once it is up** — the
window and the renderer ready, and `OnStart` finished — so the line after it may write
state and expect it to exist. `Wait()` is for when there is nothing left to do but let the
window live.

Every call is safe from any thread. Engine state belongs to the loop thread, so each call
hands its work across and waits: a round trip to the next frame, which is the right price
for a backend and the wrong one for a render path. That is why there is no drawing here.

## The API

| | |
| --- | --- |
| `Rda.Init(config)` | starts the engine; returns once it is up |
| `Rda.LoadInterface(blueprint, source?)` | show one compiled layout |
| `Rda.OpenRoutes(Routes.All, layoutDir, sourceDir?)` | show a set of screens |
| `Rda.SetTransitionMs(ms)` | how long one screen takes to cross-fade into the next |
| `Rda.Back()` / `Forward()` / `CanGoBack` / `CanGoForward` | history |
| `Rda.Running` / `Stop()` / `Wait()` | the window's lifetime |
| `Rda.Invoke(command)` | ask for a command yourself |
| `Rda.OnCommand(name, handler)` | bind by name |

`StartupConfig` takes `Name`, `Theme`, `Languages`, `Vsync`, `Font`, `FontHeight`, and the
`OnStart` / `OnUpdate` / `OnShutdown` delegates.

Everything else — `State`, `Commands`, `Tables`, `Routes`, `Schema.Define()` — comes from
the file `rda csharp` generates from your declaration.

## Finding the engine

`rendeer_c.dll` beside the assembly, which is where .NET looks first and where the
`.csproj` copies it from `bin/`. `RDA_ENGINE` -- the file, or the folder holding it --
is looked at before that, for a program that would rather load it from the checkout.
