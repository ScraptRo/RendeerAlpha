# rda — a RendeerAlpha backend in Node

```js
import * as rda from 'rda'
import { State, Commands, define } from './state.mjs'   // generated by `rda node`

rda.init({ name: 'My application', theme: 'res/themes/app.rdth' })
define()
rda.loadInterface('res/layouts/home.rdab')

Commands.save(() => console.log(State.notes))

await rda.run()
```

Node is a **backend** here. The interface is a compiled layout — written in TSX, checked
against a generated schema, styled by a theme, bound to signals and animated by the
engine. Node does not draw it; it loads it, writes the state it reads, and answers the
work it asks for. That is the same job C++ has, and the layout cannot tell which of them
is behind it.

## Installing

```bash
npm install /path/to/RendeerAlpha/bindings/node
```

npm links a path dependency rather than copying it, so `node_modules/rda` points into
the checkout and a rebuilt engine is seen at once. The package's one dependency, koffi,
is installed inside it by the bring-up. koffi is the FFI: it ships a prebuilt binary for
each platform, so that install downloads rather than compiles — no node-gyp, no
compiler, no Python. Node has no FFI of its own, which is the one thing a Node backend
needs that a Python one does not.

`state.mjs` comes from `npx rda build .`, which runs the engine's tool over your `res/`
and writes it beside `app.mjs`.

## The two loops

The engine owns a thread and a loop of its own; Node owns its own. They do not merge, and
the shape of this package follows from that.

**`init()` returns.** It waits until the engine is up — the window and the renderer ready
— so the line after it may declare state and load an interface. Then the engine keeps
running on its thread while Node carries on. A server, a watcher or a REPL is not blocked
by an open window.

**Every call is synchronous**, and costs a round trip to the engine's next frame. That is
the right price for a backend and the wrong one for a render path, which is why there is
no drawing in this package at all. Reads are the ones worth noticing: keep a number you
write often in a JavaScript variable as well, and write it through rather than reading it
back.

**A command handler is not a callback.** This is the one place Node differs from C++ and
Python, and it is not a shortcut:

> A JavaScript value may only be touched on the thread that owns it. An FFI trampoline
> invoked from the engine's thread does not crash — it *deadlocks*. The engine's thread
> blocks trying to reach the JS thread, which is itself blocked inside the call that is
> waiting for the engine. Measured, not assumed.

So the engine records that a command fired and returns at once, and `run()` collects it
here, on Node's loop, where running a handler is legal. The difference is about a
millisecond and one gain: a handler may do anything Node can do, `await` included,
because it is not holding up a frame.

## The API

| | |
| --- | --- |
| `init(config)` | starts the engine; returns once it is up |
| `loadInterface(blueprint, source?)` | show one compiled layout |
| `openRoutes(ROUTES, layoutDir, sourceDir?)` | show a set of screens |
| `setTransitionMs(ms)` | how long one screen takes to cross-fade into the next |
| `back()` / `forward()` / `canGoBack()` / `canGoForward()` | history |
| `running()` / `stop()` / `wait()` | the window's lifetime |
| `run({ intervalMs })` | a promise that collects commands and resolves when the window closes |
| `poll()` | run pending handlers once, if you would rather own the timing |
| `invoke(name)` | ask for a command yourself — a menu, a hotkey, a scheduled job |

`invoke()` queues exactly as a click does, so the handler runs on the next `poll()` rather
than before `invoke` returns. Refused, not ignored, when nothing is bound to that name.

`config` takes `name`, `theme`, `languages`, `vsync`, `font` and `fontHeight`.

Everything else — `State`, `Commands`, `Tables`, `ROUTES`, `define` — comes from the
module `rda node` generates from your declaration.

## What the generated module gives you

```js
State.count = 7             // a real accessor per signal
State.count += 1
State.notAThing = 1         // TypeError, where it is written

Commands.save(() => { … })  // a function per command

Tables.products.fill(rows)  // an object per table
Tables.products.rows        // how many
Tables.products.title(0)    // one cell
```

`State` is a real object of accessors rather than a Proxy, so an editor completes the
names and knows each one's type, and the object is non-extensible — ES modules are
strict, so assigning a name that is not declared throws rather than quietly becoming a
property nobody reads.

`fill()` takes an array of objects with the declared keys, or of arrays in column order —
whichever the application already has. It writes a column at a time, because every call
crosses to the engine's thread: ten thousand rows of three columns is three round trips
this way and thirty thousand the other.

## Finding the engine

`engine.js` looks in this order: `RDA_ENGINE` (a file or a directory), beside the
package, the checkout's `bin/` (the package is `bindings/node`, two levels below it),
beside the working directory, then whatever the loader can find. The bring-up stages the
library into `bin/`, so none of that needs setting. `npx rda where` prints the answer.
